# 蚂蚁（Mayi Agent）

面向企业知识工作与自动化协作场景打造的智能桌面 Agent，提供安全的本地文件操作、工具执行、专业文档处理和可扩展能力体系。

- Electron 主进程与安全 Preload 桥接。
- Vue Router 路由守卫与 Pinia 登录状态。
- DeepSeek Anthropic 兼容接口和 Claude Agent SDK 流式执行。
- 会话创建、恢复、排队、取消、删除和消息持久化。

- 工具权限弹窗、单次授权、本会话授权、高风险二次确认和超时拒绝。
- 安全 Markdown 渲染、表格展示、消息复制和外部链接隔离窗口。
- PDF、DOCX、PPTX、XLSX 内置文档技能及构建资源检查。

- Windows NSIS 打包配置。

#### 市政工程专业工法知识库技术方案

##### 建设原则

- 不直接全网抓取标准全文，不绕过登录、付费、版权和下载限制。
- 标准目录、状态和公告只从国家、行业、安徽省、合肥市主管部门官方白名单同步。
- 标准全文仅接收官方公开文件、用户合法上传文件或已获得检索授权的内容。
- 不直接使用刚抓取的网页内容编写施组，必须经过暂存、哈希、解析、状态核验和人工审核后发布。
- 不以标准条文代替施工工法。标准负责合规底线，图纸负责项目参数，工法卡负责施工步骤，策划数据负责工期和资源。
- 第一阶段使用结构化过滤和全文检索，不训练专用模型；后续再按效果增加向量检索和重排序。

##### 总体架构

```text
官方标准元数据同步 ──→ 标准登记库 ───────────────┐
官方公开/合法授权全文 ─→ 条文解析与版本库 ───────┤
企业工法和专家经验 ───→ 专业工法卡库 ───────────┼→ 项目化检索 → 施组策划与正文
招标、补疑、图纸、清单 → 项目事实和约束库 ───────┤
标准状态与正文引用 ───→ 有效性和适用性检查器 ───┘
```

运行时只把与当前项目地区、专业、施工阶段和具体问题相关的少量条款及工法卡放入模型上下文，不加载完整标准库。

##### 四层数据体系

1. **标准登记层**：保存编号、名称、层级、地区、专业、状态、发布日期、实施日期、废止日期、替代关系、强制性质、官方来源和核验时间。
2. **标准条文层**：按章、节、条款、条文说明、表格和附录切分合法全文；每个条款保留页码、来源哈希和标准版本。
3. **专业工法层**：将标准约束、施工步骤、项目输入、质量验收、安全风险、资源需求和验收证据整理为经过审核的工法卡。
4. **项目覆盖层**：使用招标、补疑、签章图纸、清单、地勘、管线和用户确认覆盖工法卡参数；项目未提供的关键值不得由通用知识补齐。

##### 计划新增的三个技能

###### `construction-standard-registry`

负责：

- 同步官方标准目录、标准公告、实施日期、局部修订、废止和替代关系。
- 正规化国家、行业、安徽省和合肥市标准编号。
- 维护 `active`、`revised`、`superseded`、`abolished`、`unknown` 状态。
- 区分 `mandatory`、`recommended`、`partially-mandatory`、`unknown` 性质。
- 记录全文访问方式：`public`、`licensed`、`metadata-only`。
- 按项目投标截止日期生成不可变的标准版本快照。

###### `municipal-construction-methods`

负责：

- 根据专业、适用条件和项目事实选择工法卡。
- 输出施工流程、工序衔接、控制参数、质量检查点、安全风险、环境措施和验收证据。
- 输出人员岗位、机械类型、材料条件和产能依据，但不虚构投标人实际资源。
- 标记不适用条件、必要输入和禁止假设。
- 将缺少的设计参数、地质条件、管线信息和现场条件转入 `pending_confirmation`。

###### `construction-standard-validation`

负责：

- 从施组正文和工法卡中提取标准引用。
- 检查标准名称、编号、地区、专业、实施时间、废止和替代关系。
- 检查是否错误引用征求意见稿、条文说明、其他省市或其他工程专业标准。
- 检查招标文件明确采用的标准是否遗漏。
- 生成 `standards-validation.json`，按阻断、高、中、低输出问题和修复建议。

##### 边查边存与项目隔离

采用 Cache-Aside（旁路缓存）模式：先查询本地标准库，没有可用记录或记录超过核验周期时，再查询官方白名单并回写数据库。标准原文、条款、版本和状态属于全局可复用数据；标准在某个项目中的适用性结论、采用原因、冲突和确认结果属于项目数据，必须相互隔离。

```text
项目请求标准
	→ 按编号、地区、专业和项目适用日期查询本地数据库
	├─ 命中已审核有效版本 → 直接复用并写入项目快照
	├─ 命中过期待核验版本 → 草案可暂用并后台刷新，正式定稿等待核验
	└─ 未命中 → 查询官方白名单
		→ 保存原始响应、来源和哈希
		→ 解析元数据及合法全文
		→ 写入暂存状态
		→ 自动校验和必要的人工审核
		→ 发布到全局标准库
		→ 写入当前项目标准快照
```

标准可信状态：

- `discovered`：刚查询到，仅保留来源，不得用于正式定稿。
- `pending_review`：已解析但尚未完成效力和适用性核验，只能用于草案提示。
- `verified_official`：官方来源、编号、名称、日期和哈希已经验证，可以引用并保留核验记录。
- `approved`：条文结构和适用范围已经审核，可以用于正式施组。
- `superseded`：已被替代，只用于历史项目和版本追溯。
- `abolished`：已废止，禁止作为当前项目现行依据。
- `rejected`：来源或内容不可靠，禁止使用。

数据库查询必须包含项目适用日期，不能只按标准编号取最新版：

```sql
SELECT *
FROM standard_versions
WHERE standard_id = ?
	AND effective_date <= ?
	AND (abolished_date IS NULL OR abolished_date > ?)
	AND verification_status IN ('verified_official', 'approved')
ORDER BY effective_date DESC
LIMIT 1;
```

缓存和回写规则：

- 缓存核验周期、负缓存周期和正式投标强制刷新时间必须配置化，不写死在业务代码中。
- 查询不到时可以短期保存 `not_found` 结果以避免重复请求，但只能表示本次官方查询未找到，不能证明标准不存在。
- 多个任务同时查询同一标准时使用 `normalized_code + jurisdiction + applicable_date` 查询锁，避免重复下载和解析。
- 标准文件使用 `normalized_code + effective_date + source_hash` 去重；哈希未变化时只更新核验时间。
- 新文件必须保留旧版本，不覆盖历史条文和项目快照。
- 官方查询失败时返回已有缓存并标记 `refresh_failed`；正式定稿是否可继续由标准状态、缓存时间和项目风险共同决定。

每个项目生成独立的 `project-standard-snapshot.json`：

```json
{
	"projectId": "项目ID",
	"applicableDate": "投标截止日期",
	"standards": [
		{
			"code": "标准编号",
			"versionId": "固定版本ID",
			"sourceHash": "标准文件哈希",
			"selectionReason": "tender|design|mandatory|regional|method",
			"verificationStatus": "approved",
			"verifiedAt": "核验时间"
		}
	]
}
```

另一个项目仍需重新执行招标引用提取、地区和专业适用性判断，但可以复用全局库中相同且有效的标准文件、条文和审核结果，不重复下载、OCR 和切分。全局标准更新后只提示已有项目发现新版本，不允许静默替换项目快照。

##### 官方数据同步流程

```text
官方域名白名单
	→ 下载公告、目录或公开全文
	→ 校验响应类型、大小、文件头和哈希
	→ 写入暂存区
	→ 提取标准元数据和条款结构
	→ 比较既有版本和替代关系
	→ 人工审核来源、效力和适用范围
	→ 发布到正式知识库
	→ 标记受影响工法卡和项目快照
```

- 同步任务不得执行网页或附件中的脚本、宏和可执行文件。
- 只允许配置中的官方 HTTPS 域名，不自动跟随到非白名单下载源。
- 文件变化必须保留旧版本，不原地覆盖；使用哈希判断实际内容变化。
- 征求意见稿、政策解读和新闻稿只能作为参考来源，不能标记为现行标准。
- 自动同步结果默认进入 `pending_review`，未审核内容不得参与正式施组定稿。

##### 运行时检索与生成流程

```text
读取项目地区、专业、投标截止日期和工程实体
	→ 提取招标和设计文件明确采用的标准
	→ 查询项目标准快照和全局标准缓存
	→ 缓存未命中或过期时查询官方白名单并回写
	→ 补充现行强制规范和适用地方标准
	→ 选择满足适用条件的审核工法卡
	→ 使用项目事实填充工法参数
	→ 缺失参数进入存疑确认
	→ 生成施工策划和正文
	→ 运行标准有效性及引用检查
```

检索优先级：

1. 法律法规和强制性工程建设规范。
2. 招标补疑、签章设计和项目专项技术要求。
3. 招标文件明确采用的国家、行业和地方标准。
4. 现行国家、行业、安徽省和合肥市适用标准。
5. 建设单位制度、已审批企业工法和设备技术文件。
6. 参考案例和经验参数。

项目专项要求可以更严格，但不能降低强制性要求；来源冲突时保留双方证据并进入 `conflicting`，不得由模型自行裁决。
