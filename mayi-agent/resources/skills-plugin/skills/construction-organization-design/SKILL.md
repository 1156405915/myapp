# 施工组织设计

先阅读 [阶段契约](references/execution-workflow.md)。仅处理宿主指定阶段及输入版本，不以聊天记忆或自行维护的文件状态替代主进程记录。

1. `requirements`：分析招标正文、补疑与适用附件，提取工期、范围、评分、格式和必须响应的要求，保留出处及条款修改关系，集中提出冲突问题。
2. `boq`：读取宿主解析的清单行，按专业、工序和做法归类。保留项目特征、单位、数量及源表位置，不重复汇总控制价，不合并不同规格单位，不改写原始数量。
3. `draft`：根据要求和实际施工分组建立目录，先形成统一部署及计划，再逐章编写、制作附表。每项要求和适用分组关联章节，图表与正文共用同一计算后计划。
4. `deliver`：提交已确认结构化内容给固定模板构建与检查工具，返回宿主登记的成果及限制说明。模型完成不代表正式交付。

## 工具与权限

- 资料解析、数量汇总、计划计算、文档渲染由受控业务工具执行；未提供对应工具时明确受阻，不通过 Bash 绕行。
- 不创建 task-state.json，不自行推进阶段，不覆盖源资料或已发布文件。
- 标准、工法和图纸按需查询；不强制所有项目先完成独立知识审批流程，也不将未核验内容伪称已核验。
- 地区专项预审仅在招标明确适用时调用，不自动套用其他地区或项目规则。

## 输出与检查

使用宿主提供的 Schema 和 [数据契约](references/workflow-contract.md)，返回有证据的结构化结果及未决问题。章节组织可参考 [章节框架](references/chapter-framework.md)，但以实际招标要求和工程内容为准。

- 工期、工程量、规格、人员和设备承诺必须有来源或明确确认；不能用清单数量单独推断工期。
- 资料提取完成不等于模型完整阅读；不可解析格式、失败页及未分析内容必须披露。
- 补疑只覆盖明确修改的条款，冲突不能按文件名猜测。
- 草稿保留假设及限制；阻断问题未关闭不能宣称正式可交付。
