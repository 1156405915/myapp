# Mayi Agent 工作流审查与完善建议

> 审查日期：2026-09-07  
> 审查范围：项目 README、主进程、Renderer、Preload、施组 Skills、知识服务与现有测试。  
> 当前结论：聊天执行底座已经可用，施组业务已有若干真实计算与校验能力，但尚未形成“强制门禁、可靠恢复、证据可追溯、交付可验收”的完整工作流。

## 1. 当前验证基线

本次实际验证结果：

- 16 个测试文件通过。
- 86 项测试通过。
- TypeScript 类型检查通过。
- 19 个内置 Skill 资源检查通过。
- 未进行真实模型端到端测试、安装包验证或完整性能压测。

额外边界验证发现：

1. 工期为 1.5 天、材料总量为 150 时，日级资源曲线汇总为 200，但计算结果仍为 `ready: true`。
2. 项目事实完整，但计划项目对象为空、评分项和响应均为空时，一致性检查仍返回 `ready: true` 且无问题。

这说明当前自动化测试证明了基础代码可运行，但还不能证明所有业务门禁正确。

## 2. 总体成熟度判断

当前产品适合：

- 人工监督下的 Agent 对话与文档协作。
- 施组资料初步清点。
- 施工计划基础计算。
- 标准和工法的本地登记、匹配与草案使用。
- 结构化引用清单的基础校验。

当前还不适合直接宣称：

- 可以无人监督自动完成正式施组。
- 可以保证 G0—G8 全流程强制通过。
- 可以证明正文不存在遗漏引用或错误数字。
- 可以在程序崩溃后可靠恢复未完成任务。
- 可以自动完成正式标准审核、工法批准和最终交付放行。

## 3. 已经完成的能力

### 3.1 Agent 与会话基础链路

已经形成真实代码链路：

- 创建会话并保存用户消息。
- 同一会话串行执行。
- 不同会话并行执行。
- Agent 流式文本和活动状态推送。
- Thinking、工具调用、工具结果、错误、Token、费用和耗时持久化。
- 正常执行完成后的 SDK 会话续聊。
- 基础取消、会话删除和权限请求生命周期。

当前“恢复”主要是正常续聊恢复，不是任务级中断恢复。

### 3.2 工作区与安全边界

已经完成的基础防线：

- 会话创建后固定工作目录。
- 工作区外路径、目录穿越和符号链接逃逸检查。
- 危险命令识别和用户授权。
- Renderer 沙箱、上下文隔离和 Preload 白名单。
- Markdown 原始 HTML 禁用及 DOMPurify 净化。
- API Key 由主进程读取并使用 `safeStorage` 保存。
- 日志脱敏、截断、Trace ID 和轮转。

当前 Bash 仍在宿主机执行，不是操作系统级沙箱。

### 3.3 附件与多模态

已经完成：

- 文件选择、拖拽和剪贴板图片导入。
- 文件类型、大小、签名和工作区归属检查。
- 附件复制到会话工作区受控目录。
- 附件元数据和消息绑定。
- 常见图片规范化并发送到模型。
- 历史消息中的附件定位。

仍缺少内置文档预览、页级证据、草稿附件恢复和深层 Office 包验证。

### 3.4 Skills 与角色

已经完成：

- 19 个内置 Skill 的动态发现和构建检查。
- Skill 搜索、分类、启停和依赖管理。
- 循环依赖拒绝和依赖禁用保护。
- 外部命令依赖探测。
- 角色系统提示注入。
- 施组编制专家角色的基础技能组合。

当前仅支持随应用发布的可信内置 Skill，不支持用户安装本地或网络 Skill。

### 3.5 施组确定性能力

已经存在真实执行器的部分：

- 资料文件清单、SHA-256、重复文件和变化检测。
- WBS DAG 校验。
- FS、SS、FF、SF 逻辑关系处理。
- CPM 正推、逆推、关键路径和时差计算。
- 根据工程量和班组产能推算工期。
- 劳动力、机械和材料日级资源曲线。
- 标准登记、审核状态、缓存和项目快照。
- 工法卡匹配和项目工法快照。
- 标准引用清单校验。
- 标准状态变化的影响记录。

这些执行器尚未被统一的 G0—G8 主进程状态机串联。

## 5. 已确认需要修复的问题

### 5.1 小数工期材料守恒错误

当前材料资源按任务总工期平均分配到每个覆盖的自然日桶，没有按实际重叠时间加权。

示例：

- 工期：1.5 天。
- 材料总量：150。
- 当前输出：第 1 天 100，第 2 天 100，合计 200。

建议：

- 计算任务时间段与每天区间的实际重叠时长。
- 每天材料量使用 `总量 × 重叠时长 ÷ 总工期`。
- 增加材料、人工工时和其他累计型资源的守恒测试。
- 明确机械台班和瞬时劳动力是否按占用量或累计量统计。

### 5.2 空计划能够通过一致性检查

当前检查只要求 `matrix.items` 和 `plan.responses` 是数组，空数组合法；计划关键字段为空时也不会报告与事实不一致。

建议：

- 正式模式要求评分项非空。
- 要求计划关键字段存在，而不是只在双方都有值时比较。
- 区分“未检查”“无数据”“检查通过”。
- `ready` 必须同时满足完整性、覆盖率和一致性条件。
- 增加空计划、空评分矩阵、空响应和关键字段缺失测试。

## 6. 高优先级工作流缺口

### 6.1 同工作区跨会话产物路径冲突

标准快照、工法快照和引用报告的修订号按会话分别计算，但文件路径只有 `r1`、`r2` 等修订号，没有会话或项目目录。

风险：

- 两个会话使用同一工作区时，都可能生成自己的 `r1`。
- 文件可能被覆盖，数据库记录与磁盘文件可能不一致。
- 用户打开的产物可能属于另一个会话。

建议目录：

```text
.mayi/knowledge/construction/<sessionId>/standards/
.mayi/knowledge/construction/<sessionId>/methods/
.mayi/knowledge/construction/<sessionId>/validation/
```

同时在读取和冻结时校验快照所属会话。

### 6.2 取消后立即发送可能造成队列停滞

当前取消会设置取消标记并删除已有队列，但旧执行彻底退出前，新消息仍可重新入队。此时会话还在活动集合中，不会启动新消费者；旧消费者退出后也没有重新调度残留队列。

建议：

- 为每次执行生成独立 `runId`。
- 明确会话状态：排队、运行、取消中、已取消、失败、完成。
- 取消中发送时选择明确策略：拒绝、等待取消完成或创建新的执行代次。
- `finally` 中检查残留队列并安全重启消费者。
- 增加“取消后立即发送”的回归测试。

### 6.3 任务状态没有持久化

当前用户消息先保存，再进入内存队列。程序退出后：

- 消息仍在历史中。
- 排队状态和执行状态丢失。
- 无法判断消息是未执行、已取消还是执行中断。

建议增加持久化运行记录：

```text
run_id
session_id
user_message_id
status
queued_at
started_at
finished_at
runtime_session_id
attempt
cancel_reason
error
```

启动时把未正常完成的任务标记为 `interrupted`，由用户选择重试，而不是静默改成空闲。

### 6.4 SDK 恢复 ID 与助手消息不是原子提交

成功路径先保存新的 SDK 恢复 ID 和会话状态，再保存助手消息。中间失败时可能出现：

- SDK 上下文已经推进。
- 本地没有对应助手消息。
- 后续续聊上下文与界面历史不一致。

建议把执行结果、恢复 ID、助手消息和最终状态放入同一存储事务。

### 6.5 取消后的迟到事件可能污染界面

当前最终结果会检查取消状态，但流式增量和活动事件没有执行代次标识。

建议：

- 所有运行事件携带 `runId` 和递增序号。
- Renderer 按会话和 `runId` 保存运行态。
- 取消后忽略旧 `runId` 的增量、活动和最终结果。

### 6.6 标准负缓存可能遮蔽新导入数据

标准查询先检查负缓存，再查询本地标准。发生“先查未命中，后导入标准”时，相同查询可能继续返回负缓存，默认最长一天。

建议：

- 标准导入、审核和状态变更时删除相关负缓存。
- 或将本地有效版本查询放在负缓存之前。
- 增加“未命中后导入”的回归测试。

### 6.7 工法事实哈希不足以证明事实未变化

当前 `factsHash` 只根据事实 ID 列表计算，不包含：

- 事实值。
- 单位。
- 来源证据。
- 确认状态。
- 事实版本。

同一个事实 ID 的数值变化时，哈希可能不变。

建议让哈希绑定规范化后的完整事实快照，并在冻结工法时重新执行适用和排除条件检查。

### 6.8 引用校验不能证明正文引用完整

当前校验输入是调用方提交的引用清单，不读取最终正文。遗漏在清单之外的标准不会被发现。

建议：

- 从 DOCX/PDF 或结构化正文自动提取所有标准引用。
- 将校验报告绑定交付文件哈希。
- 正文变化后自动将旧报告标记为失效。
- 区分“引用正确性”和“引用覆盖完整性”。

## 7. 前端工作流需要完善的部分

### 7.1 会话切换竞态

快速选择会话 A、B 时，如果 A 的历史请求后返回，可能覆盖当前已选择的 B 会话消息。

建议：

- 为历史加载增加请求代次。
- 返回时确认当前会话仍匹配。
- 按消息 ID 合并历史快照与实时事件。
- 加载期间显示明确状态，不继续显示旧会话内容。

### 7.2 运行会话切走后无法恢复临时输出

当前只有一份全局流文本。切换会话会清空，非活动会话的增量被忽略。

建议按 `sessionId` 保存：

- 当前 `runId`。
- 累计流文本。
- Agent 活动状态。
- 队列数量。
- 取消状态。

### 7.3 排队发送的界面语义不明确

主进程允许排队，但运行中按 Enter 仍可发送，界面又会清空当前流文本。

建议：

- 明确显示“发送并排队”。
- 展示队列数量和每条任务状态。
- 新消息入队时保留当前执行的回复。

### 7.4 跨会话权限请求信息不足

权限队列可以接收其他会话请求，但弹窗未充分展示所属会话和工作区。

建议显示：

- 会话标题。
- 固定工作区。
- 工具名称和目标路径。
- 风险级别。
- “本会话允许”的具体授权范围。

### 7.5 附件草稿缺少恢复和清理闭环

附件已复制到磁盘并保存元数据，但待发送列表主要存在组件内存中。切换页面或异常退出后可能留下无法继续发送的附件记录。

需要明确：

- 草稿附件是否持久化。
- 重启后是否恢复。
- 删除空草稿会话时是否同步清理。
- 导入过程中切换会话时附件归属如何处理。

### 7.6 角色和 Skills 语义需要澄清

角色会话执行时使用角色要求的技能集合，不完全等于全局 Skills 开关状态。

建议 UI 分别展示：

- 全局默认启用技能。
- 当前角色强制依赖技能。
- 当前会话实际生效技能快照。

## 8. 安全边界需要进一步完善

以下属于静态审查发现的边界加固项，未进行漏洞利用验证：

- 高风险“本会话始终允许”的二次确认应由主进程验证，不能只依赖前端状态。
- 工具路径在权限等待前检查，授权后应重新校验，减少检查与执行之间的状态变化风险。
- IPC 除校验主窗口 `webContents` 外，还应确认可信主 frame。
- Office 文件不能只根据 ZIP 签名和 `word/`、`ppt/`、`xl/` 字符串判断合法性，应解析真实 ZIP 目录和必要 OOXML 条目。
- 附件大小限制应明确是单次导入、单条消息还是单会话累计限制。
- 权限授权范围建议从工具名细化为工具、命令模式、路径范围和风险级别。

## 9. 性能优化建议

以下是静态代码风险，应先建立性能基线再确认收益。

### 9.1 历史消息读取

问题：

- 每次发送只为了判断是否第一条消息，就读取完整历史。
- 历史读取逐消息加载内容块，存在 N+1 查询风险。
- Renderer 全量挂载消息和工具块。

建议：

- 使用消息存在性查询判断首条消息。
- 内容块批量查询。
- 历史消息游标分页。
- 长列表窗口化。
- 大型工具输入和结果仅在展开时挂载。

### 9.2 流式 Markdown 渲染

问题：

- 每个增量都会追加字符串。
- 累计全文会重新进行 Markdown 解析和 HTML 净化。
- 每次增量都可能触发平滑滚动。

建议：

- 主进程或 Renderer 将增量按 30—100 毫秒合并。
- 稳定内容块缓存渲染结果。
- 仅在用户接近底部时自动跟随。
- 提供“回到最新”按钮。

### 9.3 主进程同步附件处理

问题：

- 文件读写、Office 内容检查、图片解码、缩放和编码主要在 Electron 主进程同步执行。
- 大图片或损坏图片可能阻塞界面和 IPC。

建议：

- 普通文件 I/O 异步化。
- 图片和 Office 深层检查移到 Worker 或独立进程。
- 解码前读取图片头并限制像素尺寸。
- 增加超时、内存和并发限制。

### 9.4 资料清点

问题：

- 每次重新读取全部文件并计算 SHA-256。
- 固定类别到阶段映射不能准确表达事实和章节依赖。
- 输出目录和知识产物可能被误当成输入变化。

建议：

- 保存文件索引和上次哈希。
- 先根据大小、修改时间和文件标识筛选变化，再按需重算哈希。
- 明确排除 `.mayi` 生成目录和其他会话产物。
- 建立事实、章节、图件和阶段的依赖图。

### 9.5 施工计划

问题：

- 资源曲线按自然日逐日展开。
- 工期和时间轴没有合理业务上限。
- 超大周期可能产生巨量循环和 JSON。

建议：

- 设置任务数量、工期和总时间轴上限。
- 长周期按周或月聚合展示。
- 仅在用户需要时输出完整日级曲线。
- 避免对超大数组使用扩展参数计算峰值。

### 9.6 全局执行并发

问题：

- 不同会话可并行，但没有全局并发上限。
- 会话队列没有长度和资源预算限制。

建议：

- 设置 Agent 全局并发上限。
- 设置单会话和全局队列上限。
- 根据 Provider 限流和本机资源进行调度。
- 将任务中心作为真实调度器状态的展示层，而不是单独制作静态页面。

### 9.7 PDF、LibreOffice 和数据库

建议：

- PDF 分页转图，避免整本文档图像同时驻留内存。
- LibreOffice 使用会话隔离的用户配置目录并设置超时。
- 公式重算后验证公式缓存值是否实际生成。
- 测量大数据库启动时完整性检查和备份耗时。
- 避免在消息内容块和 Trace 中重复保存完整大型工具结果。

## 12. 推荐的最终工作流形态

```text
创建项目/会话
→ G0 资料接收、解析和证据登记
→ G1 招标红线及评分项提取
→ G2 项目事实确认和版本冻结
→ G3 冲突处理与阻断项关闭
→ G4 工法、标准、计划和资源策划
→ G5 正文生成及评分项覆盖检查
→ G6 图件生成及数据一致性校验
→ G7 全文、暗标、引用和逐页审核
→ G8 交付文件冻结、清单和最终放行
```

每个阶段都应保存：

- 输入文件及哈希。
- 项目事实版本。
- 标准和工法快照。
- 执行记录与 `runId`。
- 结构化产物。
- 问题、严重程度和处理状态。
- 人工确认和审核记录。
- 最终产物及哈希。

阶段放行应由确定性代码决定；模型负责分析、生成和提出建议，但不能仅凭自然语言声明阶段已经通过。

## 13. 核心方向

当前最值得投入的方向不是继续增加静态页面或 Skill 数量，而是：

1. 先保证现有计算不会算错。
2. 保证不同会话和项目不会串数据。
3. 保证取消、失败和崩溃后状态可解释、可恢复。
4. 用统一状态机把已有执行器连接起来。
5. 让每个结论都能追溯到输入、事实、标准和文件证据。
6. 最终由确定性门禁决定是否允许正式交付。
